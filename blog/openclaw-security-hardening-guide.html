OpenClaw Security Hardening: 10 Things You're Probably Missing

You got OpenClaw running. Great. Now let's make sure you're not leaving the front door wide open.

Feb 17, 2026 12 min read Security Self-Hosted Guide

Self-hosting OpenClaw is one of the best ways to keep your AI workflow private and under your control. But the default install is optimized for getting you running, not for production security. Most people stop after openclaw gateway start and call it a day.

That's a problem. Your OpenClaw instance has access to your shell, your files, your network, and potentially your cloud credentials. An exposed gateway is an open invitation.

Here are 10 things you should do today to lock it down.

1. Lock Down Ports with Firewall Rules

If your OpenClaw host is internet-facing, you need to restrict which ports are accessible. The gateway listens on a port (default 3000), and you probably have SSH on 22. Everything else should be closed.

UFW (Ubuntu/Debian)

# Reset to deny-all baseline
sudo ufw default deny incoming
sudo ufw default allow outgoing

# Allow SSH (change port if you've moved it)
sudo ufw allow 22/tcp

# Allow OpenClaw gateway ONLY from your IP or VPN range
sudo ufw allow from 10.0.0.0/24 to any port 3000 proto tcp

# Enable
sudo ufw enable
sudo ufw status verbose

iptables (if you prefer)

# Drop everything except established connections, SSH, and gateway from trusted subnet
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
iptables -A INPUT -p tcp --dport 3000 -s 10.0.0.0/24 -j ACCEPT
iptables -A INPUT -j DROP
Don't skip this. A publicly accessible gateway port means anyone who discovers it can attempt to interact with your OpenClaw instance.

2. Enforce SSH Key Authentication

If you're managing your OpenClaw server over SSH (and you probably are), password auth is a liability. Switch to key-only.

# Generate a key pair on your local machine (if you haven't)
ssh-keygen -t ed25519 -C "openclaw-admin"

# Copy your public key to the server
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@your-server

# Then on the server, disable password auth:
sudo sed -i 's/^#*PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo sed -i 's/^#*ChallengeResponseAuthentication.*/ChallengeResponseAuthentication no/' /etc/ssh/sshd_config
sudo systemctl restart sshd
Bonus: Move SSH to a non-standard port (e.g., 2222) to cut down on automated scanning noise. Update your firewall rules accordingly.

3. Disable Root Login

OpenClaw should never run as root, and root shouldn't be logging in directly over SSH. Period.

# Disable root SSH login
sudo sed -i 's/^#*PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
sudo systemctl restart sshd

# Create a dedicated user for OpenClaw if you haven't
sudo useradd -m -s /bin/bash openclaw
sudo usermod -aG sudo openclaw

# Run OpenClaw as that user
su - openclaw
openclaw gateway start

Running as a non-root user limits blast radius. If something goes wrong — a malicious tool call, a prompt injection that escapes the sandbox — the damage is contained to that user's permissions.

4. Secure the Gateway API

The gateway is the brain of your OpenClaw instance. It handles API requests, routes tool calls, and manages sessions. Treat it like the crown jewels.

Bind to localhost only

If you're accessing OpenClaw through a VPN or SSH tunnel, the gateway doesn't need to listen on 0.0.0.0:

# In your OpenClaw config (~/.openclaw/config.yaml or equivalent)
gateway:
  host: 127.0.0.1
  port: 3000

Enable HTTPS with a reverse proxy

# Nginx reverse proxy with TLS (Let's Encrypt)
server {
    listen 443 ssl http2;
    server_name openclaw.yourdomain.com;

    ssl_certificate /etc/letsencrypt/live/openclaw.yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/openclaw.yourdomain.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket support for real-time sessions
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
Never expose the gateway over plain HTTP on the internet. Tokens, session data, and tool outputs travel over that connection.

5. Rotate Your Tokens Regularly

Your gateway token is the key to the kingdom. If it leaks — in a commit, a screenshot, a log file — anyone with it can control your instance.

# Regenerate your gateway token
openclaw gateway token --rotate

# Update all connected clients/nodes with the new token
# Check for tokens accidentally committed to git:
git log --all -p | grep -i "gatewayToken\|OPENCLAW_TOKEN" | head -20

Best practices

  • Rotate tokens at least every 90 days, or immediately after any personnel change
  • Store tokens in environment variables, never in checked-in config files
  • Use .env files with strict permissions: chmod 600 .env
  • Add .env and config files to .gitignore
Automate it. Set a calendar reminder or a cron job that alerts you when it's time to rotate.

6. Use Allowlists for Tool Access

OpenClaw's tool system is powerful — shell access, file I/O, browser control, messaging. That power needs guardrails.

# In your OpenClaw config, restrict tool access per session/channel
security:
  exec:
    mode: allowlist          # deny | allowlist | full
    allowed:
      - git
      - npm
      - node
      - python3
      - openclaw
    blocked:
      - rm -rf
      - sudo su
      - curl | bash

  tools:
    disabled:
      - browser              # Disable if you don't need it
      - nodes                # Disable node control if not using paired devices

The principle of least privilege applies here. If a channel or session doesn't need shell access, don't give it shell access. If it doesn't need the browser, disable it.

Default is often too permissive. Audit which tools each channel actually needs and lock down the rest. A compromised Discord integration shouldn't have exec access.

7. Put It Behind a VPN or Tailscale

The single best thing you can do for your OpenClaw security is to take it off the public internet entirely. A VPN makes your instance accessible only to authenticated devices.

Tailscale (easiest option)

# Install Tailscale on your OpenClaw server
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up

# Your server gets a 100.x.x.x address
# Access OpenClaw at http://100.x.x.x:3000 from any device on your tailnet

# Lock down the firewall to Tailscale only
sudo ufw allow in on tailscale0
sudo ufw deny 3000/tcp   # Block public access to gateway

WireGuard (DIY option)

# Install WireGuard
sudo apt install wireguard

# Generate keys
wg genkey | tee privatekey | wg pubkey > publickey

# /etc/wireguard/wg0.conf
[Interface]
Address = 10.200.0.1/24
ListenPort = 51820
PrivateKey = <server-private-key>

[Peer]
PublicKey = <client-public-key>
AllowedIPs = 10.200.0.2/32

With a VPN, even if there's a vulnerability in the gateway, attackers can't reach it without being on your network first. It's defense in depth.

8. Monitor Your Logs

If you're not watching your logs, you won't know something's wrong until it's too late.

# Watch OpenClaw gateway logs in real-time
openclaw gateway logs -f

# Check for unusual activity — failed auth, unknown IPs
openclaw gateway logs | grep -i "error\|denied\|unauthorized\|failed" | tail -50

# Monitor SSH login attempts
journalctl -u sshd --since "1 hour ago" | grep -i "failed\|invalid"

Set up alerts

Don't just log — alert. A simple approach:

#!/bin/bash — save as /usr/local/bin/openclaw-watchdog.sh
FAILURES=$(openclaw gateway logs --since "5m" | grep -c "unauthorized")
if [ "$FAILURES" -gt 5 ]; then
  curl -X POST "https://your-webhook-url" \
    -H "Content-Type: application/json" \
    -d "{\"text\": \"⚠️ OpenClaw: $FAILURES unauthorized attempts in last 5 min\"}"
fi
# Run it every 5 minutes via cron
*/5 * * * * /usr/local/bin/openclaw-watchdog.sh
Centralize logs if you run multiple instances. Ship them to Loki, Datadog, or even a simple syslog server so you have a single place to search.

9. Implement a Backup Strategy

Your OpenClaw workspace contains memory files, configs, tool outputs, and potentially sensitive data. If the disk dies or something goes sideways, you want to recover fast.

#!/bin/bash — openclaw-backup.sh

BACKUP_DIR="/backups/openclaw"
TIMESTAMP=$(date +%Y%m%d-%H%M%S)
SOURCE="$HOME/.openclaw"

mkdir -p "$BACKUP_DIR"

# Create encrypted, compressed backup
tar czf - "$SOURCE" | \
  gpg --symmetric --cipher-algo AES256 \
  --batch --passphrase-file /root/.backup-passphrase \
  -o "$BACKUP_DIR/openclaw-$TIMESTAMP.tar.gz.gpg"

# Sync to offsite (S3, B2, rsync to another server)
aws s3 cp "$BACKUP_DIR/openclaw-$TIMESTAMP.tar.gz.gpg" \
  s3://your-bucket/openclaw-backups/

# Prune local backups older than 30 days
find "$BACKUP_DIR" -name "*.gpg" -mtime +30 -delete

echo "Backup complete: openclaw-$TIMESTAMP"

What to back up

  • ~/.openclaw/ — configs, workspace, memory, skills
  • Your reverse proxy configs (nginx/caddy)
  • Firewall rules (sudo ufw status or iptables export)
  • Environment files (.env) — stored separately, encrypted
Test your restores. A backup you've never restored is a hope, not a strategy. Spin up a test instance quarterly and verify recovery works.

10. Keep OpenClaw Updated

OpenClaw is actively developed. Security patches, bug fixes, and hardening improvements ship regularly. Running an old version means running with known vulnerabilities.

# Check your current version
openclaw --version

# Update to latest
openclaw update

# Or if installed via npm
npm update -g openclaw

# Restart the gateway after updating
openclaw gateway restart

Stay informed

  • Watch the OpenClaw GitHub repo for releases
  • Join the community Discord for security advisories
  • Subscribe to the changelog or RSS feed
Pin to a release channel if you want stability. But don't fall more than one minor version behind — that's where security debt accumulates.
